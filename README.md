# colorlab-embed

Shoppal Mart の記事本文に「貼るだけ」で動くよう、パーソナルカラー診断アプリ（v21）と
NG色警察（v2）を自己完結IIFEにビルドし、jsDelivr(CDN)で配信するためのリポジトリ。

- `dist/colorlab.iife.js` … 本家アプリ（12タイプ診断 / NGカラー / 手持ち服チェッカー / 試し塗り 等）
- `dist/ngpolice.iife.js` … NG色警察（違反切符 / 無罪放免証）
- `dist/mens.iife.js` … 清潔感カラー診断（メンズ版・商品導線なし）
- `snippet_colorlab.html` / `snippet_ngpolice.html` / `snippet_mens.html` … 記事に貼り付ける数行
- `test/local_article.html` … Shoppal記事を模したローカル検証ページ
- `test/screenshot.mjs` … Playwright検証（375px SS / localStorage再訪 / 画面遷移）
- `test/screenshot_mens.mjs` … メンズ版のPlaywright検証（全ツール通し / 商品語の不在 / Lite判定）

## フェイクカメラのテストを書くときの注意（偽ゲートの作りやすさ）

`npm run verify` は Chromium の `--use-file-for-fake-video-capture` に自前生成した Y4M を流して
撮影まわりを検証している。この方式は **「常にPASSする偽ゲート」を作りやすい**。実際に v1.15.0 の
チラつき検証は、安定化を外しても合格する状態だった（2026-08-31 に発見）。原因は3つ重なっていた。

1. **塗り位置のズレ** … 頬を `x 0.30〜0.42` に塗ったが、アプリが測るのは `x 0.242〜0.340`。
   背景が中央値に混ざり、狙った色になっていなかった。
   → **塗る範囲は、アプリが実際にサンプリングする範囲を必ず覆うこと。**
2. **サンプリング周期との数学的な一致** … 4フレーム×15fps＝267ms のループを 400ms 間隔で
   拾うと、`400 mod 267 = 133ms` で位相が固定され、**毎回同じフレームだけ**を拾っていた。
   → **ループ周期がサンプリング間隔の約数・整数倍にならないようにする**
     （5フレーム×5fps＝1000ms なら 400ms 間隔で全フレームを順に拾う）。
3. **色の未較正** … フェイクカメラのYUV変換で **a\* が約3.5低く出る**。狙った a\*23.2/27.5 が
   実際には 20.0/23.7 で届き、閾値(26)を一度もまたいでいなかった。
   → **「塗った色」ではなく「実際に届く色」で閾値をまたがせること。**
     較正には `test/_probe_calib.mjs` を使う（候補色ごとに実際に届く a\* を測る）。

**書いたゲートは、直そうとしている実装をわざと外して「本当に落ちるか」を必ず確認すること。**
落ちなければ、そのゲートは何も守っていない。

### 実機スクショから a* を実測する（`test/_measure_astar.mjs`）

肌の生理的範囲ゲート（`L*40-88 / a*2-26 / b*4-32`、`aiPhotoDiagnose` 内）の上下限を、
1枚の実写に過剰適合させずに決めるためのツール。実機の撮影画面スクショから映像の帯だけを
切り出して Y4M にし、フェイクカメラでアプリへ流し込んで、**アプリ本体が出した Lab をそのまま読む**
（Lab変換や `photoGeometry` をツール側へ写経しない）。

```
npm run build
node test/_measure_astar.mjs <撮影画面のスクショ.png> [...]
```

- **★このツールが出す a* は生値のまま信じないこと。** RGB→I420(4:2:0)→RGB の往復で赤みが落ちる。
  **白基準が中立に近いときは実機より 3〜5 低く出る**（2026-09-03 に `test/_probe_calib.mjs` で再測。
  白基準 RGB(235,232,228) の条件下で、理論 a*23.8/28.1/32.2/35.8/38.4/41.0 に対して
  届いたのは 20.0/23.7/27.1/30.9/34.4/38.0 ＝ **−3.0〜−5.1、平均 −4.2**）。
  ただし WB補正は白基準との相対計算なので、**白基準が中立から外れているときは逆に高く出ることもある**
  （2026-09-03 の実写では、無加工スクショ直読み a*34.2 に対しツール経由 a*39.6）。
  上限の議論には、**白基準が本物の白い紙である写真だけ**を使うこと。
- 表示中の映像は CSS で `scaleX(-1)`（鏡像）なので、流し込んだ映像もアプリから見ると左右が逆。
  頬の測定範囲は中心対称なので左右平均・ΔE・ゲート判定は変わらないが、左右のラベルだけ読み替える。
- スクショに赤枠などの注釈を描き込んだものは頬の測定範囲を汚すので使えない（データにならない）。
  実機のスクショを無加工のまま渡すこと。なお**焼き込まれたガイド（オレンジの頬リング）の影響は小さい**
  （リング上の画素を除いて中央値を取り直しても a* は 34.2→34.9 で、汚染は測定を左右していない。2026-09-03 実測）。
- **★白い紙を持っていない写真は、a* 上限の資料にならない。**`whiteRef` は「顎の下の固定枠の中央値」で、
  紙が無ければ **Tシャツや首の肌をそのまま白基準にしてしまう**。2026-09-03 の実写2枚がこれで、
  Tシャツ RGB(153,172,171) を白と見なした結果ゲインが R×1.536 / G×1.366 と偏り、
  **頬の a* が 18.3（無補正）→ 23.7（露出だけ補正）→ 34.2（アプリの補正後）へ跳ね上がっていた**。
  a*26 を超えたのは肌が赤いからではなく白基準が中立でないためで、**この値に合わせて上限を上げてはいけない**
  （上げると「赤みを12%盛った肌」で判定することになり、暖色側＝イエベへ系統的に寄る）。
  → **2026-09-03 に白基準の妥当性チェックを入れて対処済み**（次節）。a*上限そのものは 26 のまま。

## 顔写真で診断（実測方式・v1.7.0〜）

AIに写真を見せて判断させる方式をやめ、**白い紙を基準にした照明補正 + CIELab の実測**に置き換えた。
外部通信は一切発生しない（`npm run verify` で `api.anthropic.com` 0件を実測）。

| 項目 | 内容 |
|---|---|
| フラグ | `PHOTO_DIAGNOSE_ENABLED = true`（`AI_ENABLED` とは独立） |
| 判定ロジックの出典 | `src/photo_diagnose_v3.jsx`（参照用。**どのビルドからも import されない**） |
| 契約 | `aiPhotoDiagnose(base64, mediaType)` → `{type, second, confidence, hue_pct, value_pct, chroma_pct, reason}` |
| サンプリング領域 | `PH_REGION`（白紙 0.34-0.76-0.66-0.92 / 左頬 / 右頬 / 髪） |
| 品質ゲート | 暗すぎ / 白飛び / 色かぶり28%超 / 左右頬差ΔE14超 / 肌の生理的範囲外 → `gateError()` を throw して撮り直し画面へ |
| 画面 | intro（撮影条件5項目 + 染髪確認）→ guide（ライブカメラ + 丸型グラデガイド）→ analyzing → rejected |

**触るときの注意**

- `hue_pct` / `value_pct` / `chroma_pct` は「そのタイプのラベル方向の強さ」。結果画面が軸ラベル
  （Warm/Cool・Light/Deep・Clear/Soft）を1stタイプから決めるため、生の warmth/lightness/clarity を
  そのまま入れると「Cool（青み）20%」のような矛盾表示になる。質問式 `finishQuiz()` と同じ考え方。
- **ガイドの座標と `PH_REGION` は必ずセットで動かす。** 見た目だけ動かすと「ガイドに合わせたのに
  測定エリアが違う」事故になる。`npm run verify` に中心Yズレ5px以内の恒久ゲートを入れてある。
- 撮影ボタンは**映像の下の黒帯(96px)の中**に置く。映像に重ねると白紙ガイド＝測定範囲(0.76〜0.92)を
  丸ごと覆ってしまう（実測で 68×54px の重なり）。オーバーレイSVGは内側ラッパで映像と同じ高さに
  閉じ込めること（黒帯まで伸びるとガイドが50px下へズレる）。

## コーデ提案（シーン別記事のデータ参照・v1.8.0〜）

`STYLING_DATA` は BLUBEL/IEBEL のシーン別記事22本（`42_{BLUBEL,IEBEL}_scene_articles_20260822.csv`）から
機械抽出した色マスター。**86シーン / 1,204色チップ**を持つ（約76KB / gzip 約15KB）。

- シーンの選択順は 気分の自由入力 > デート細分 > 会う相手 > シーン既定。
- `styling` は記事のリード文と記事の色名・効果だけで組み立てる。**新しい文章を創作しない。**
- `sku_ids` は必ず `SKUS[site]` の実在商品から2〜3点。記事の推奨SKUが在庫にあれば最優先する
  （記事の推奨SKU 23件のうち在庫にあるのは7件だけなので、残りはシーン・骨格・悩みで選ぶ）。
- 同じ入力なら必ず同じ結果になる（`npm run verify` で決定論であることを実測している）。

## 今日のコーデ採点（色照合・v1.8.0〜）

トップスとボトムスの2領域をサンプリングし、`TYPES[type].palette10`（勝ち色10色）と
`NG_COLORS[type]`（NG色4色）との ΔE(CIE76) で採点する。

- `score = clamp(50 + トップス(±30) + ボトムス(±20), 0, 100)`。顔に近いトップスを重く配点する。
- `improve` / `one_item` は `NG_COLORS` が持つ `why`（理由）と `alt`（置換色）をそのまま使う。
- 品質ゲート: 暗すぎ / 白飛び / 枠に服が入っていない / 2領域と背景が揃って区別できない。
  **ワントーンコーデは却下しない**（背景と区別できていれば正当な写真なので採点し、その旨を添える）。
- **判定できるのは服の色とタイプの相性だけ。**シルエット・素材感は対象外で、案内画面と結果画面の
  両方に明記している。この注記を消さないこと。
- ガイド枠の座標は `SC_REGION` と一致させること（`npm run verify` に中心Yズレ5px以内のゲートがある）。

## 撮影中のライブ条件チェック（v1.9.0〜）

`guide` ステップで `livePhotoCheck()` が 400ms 間隔に間引いて動き、明るさ / 白い紙 / 顔の位置 /
左右バランスの4項目を黒帯の中（シャッターの左右）に表示する。

- **本判定（`aiPhotoDiagnose()` の品質ゲート）とは別ロジックの軽量版。**120px の縮小フレームを見る
  だけの粗い近似で、4項目すべて✓でも本判定で却下されることはあり得る。画面にもその旨を明記している。
- サンプリング領域（`PH_REGION`）と閾値は本判定と揃えてあるので、**どちらかを変えるときは両方**を見直す。
- **ガイドの図形と測定範囲は `photoGeometry(ar)` が両方まとめて作る。**別々に書かないこと。
  以前は viewBox="0 0 300 400"(3:4) 固定でガイドを描き、サンプリングは実フレームの相対座標で
  行っていた。iOS Safari は width/height が ideal 指定だと 4:3 の横長映像を返すため、3:4 の
  ガイドがレターボックスされて中央に縮小描画され、**画面に見える枠と実際に測る場所が最大36px
  ズレていた**（2026-08-30 実機で実測。頬の測定範囲が顔の外＝髪・耳・背景に乗っていた）。
  - **★ガイドの座標を1枚の実写だけで確定させないこと。** 2026-08-30 に「顔が近い1枚」だけを見て
    `cheekX` を 0.60→0.80 にしたところ、8/31 の「顔がやや遠い1枚」では枠が顔からはみ出して
    背景を拾い、左右頬の色差で却下されるようになった。同じ人でも撮影ごとに顔とガイド楕円の
    大小関係が変わる。**撮影距離の異なる複数枚で ΔE を掃引し、全条件で通る値を選ぶこと。**
    実測表は `PH_FACE` の `cheekX` の直上にコメントとして残してある。
  比率定数は `PH_FACE` に集約してあり、`npm run verify` は **3:4 と 4:3 の両方**で
  「描かれたガイド＝測定範囲」を実測する。テストは `PH_FACE` をソースから読むので、
  数値をテストへ写経しないこと（アプリだけ直してテストが古いまま、を防ぐため）。
  - コーデ採点側も同じ理由で viewBox を実アスペクトに合わせ、枠は `SC_REGION` から直接描く。
- **撮影中は全画面オーバーレイ**（`position:fixed; inset:0; z-index:99999`）。記事の他要素の上に重なる。
  顔写真診断とコーデ採点で共通の `FullscreenCamera` を使い、**`createPortal` で `document.body` 直下**
  に描画する。`#colorlab-root` の中に置くと、埋め込み先の祖先に transform / filter / perspective /
  will-change / backdrop-filter / contain のいずれかがあった場合、`position:fixed` の基準が
  ビューポートでなくその祖先になり全画面にならない。`npm run verify` に transform / filter /
  will-change の3ケースの回帰ゲートがある。
  - ポータル化に伴い、**video 要素はカメラ準備OKになってから生える**。そのため `getUserMedia` の
    直後に `srcObject` を差し込むことはできない（差し込むとカメラが永久に起動しない）。
    ストリームは ref に保持し、描画後に `attachCameraStream()` で接続すること。
  - オーバーレイは `#colorlab-root` の外に出るため **Tailwind のユーティリティが効かない。**
    インラインスタイルだけで組み、フォントも `FS_FONT` で明示すること。
  表示中は `document.body` の `overflow` を hidden にし、閉じたら必ず元へ戻す。
  ✕ボタンで `intro` に戻り、`stopPhCamera()` でストリームを止める。
  - **`object-fit: cover` を使ってはいけない。**引き伸ばすとガイドSVGと実測範囲(`PH_REGION`)がズレる。
    映像は必ず元の縦横比のまま、JS（`phBox`）で領域に収まる最大サイズを算出して表示する。
    `npm run verify` に「映像の縦横比のズレ < 0.01」の恒久ゲートを入れてある。
  - カメラ未起動・エラー時のUIは従来どおり記事カードの中に出る（全画面になるのは映像が出てから）。
- `npm run verify` は Chromium の `--use-file-for-fake-video-capture` に自前生成した Y4M を流し込み、
  「条件を満たす映像で4項目✓」「暗い映像で✓にならない」「描画60fps維持・フレーム落ち0」を実測している。
- **ライブ判定のパネルは「映像の外・シャッターの上」に置く。**シャッターを押す親指は画面下端から
  入るので、黒帯より上の要素には物理的に届かない（下に置くと撮影時に指で隠れる）。映像の外なので
  ガイド座標とサンプリング範囲の対応にも影響しない。`npm run verify` に
  「パネルがシャッターより上」「パネルが映像に重ならない」の実測ゲートがある。
- **満たしていない項目があるときは、その直し方を1行で出す**（`PH_LIVE_HINT`）。
  「○偏り」とだけ出してもユーザーは何をすればよいか分からないため。全項目✓のときだけ
  「撮影前の目安です…」の文言に戻る。
- **「顔の位置」は3状態**（✓緑=枠内 / ○オレンジ=ズレ / —グレー=判定待ち）。
  この判定は白い紙でWB補正したあとの肌を見るため、**白紙が取れていないと測れない**。
  測れないときに false（○ズレ）を返すと「位置は合っているのにズレていると嘘を伝える」ことになる
  （2026-08-29 実機で発生）。`livePhotoCheck()` は測れないとき **null** を返すこと。
  - **★短いラベルに「理由」を詰め込まないこと。** —グレーの表示は当初「白い紙が先」だったが、
    初見のユーザーには何のことか全く伝わらなかった（2026-09-02 実機の指摘）。ラベルは状態だけ
    （「判定待ち」）にし、**なぜ待ちなのか／次に何をすればよいのかは、必ずパネル下部の補足行
    （`photoLiveHint()`）に文章で出す**。補足行では `paper` 未検出を最優先で扱い、行動文言
    （明るさ or 白い紙）に `PH_LIVE_PAPER_NOTE`「白い紙が映ると、「顔の位置」も判定できる
    ようになります」をつなげて1行にする。暗くて紙が取れない場合は、紙を持たせるより先に
    明るさを直させる。`npm run verify` に「ラベルに『白い紙が先』を出していない」
    「理由が補足行に文章で出る」の回帰ゲートがある（`32_photo_live_paper_first.png` / `24_photo_live_dark.png`）。

### 白基準（顎の下の白い紙）が本当に白い紙かを見る（2026-09-03〜）

白基準は、肌を測る前に照明の偏りを打ち消すための**モノサシ**。ここが白でないと、
歪んだモノサシのまま肌を測ることになる。従来は「色かぶり率 28% 以下」しか見ておらず、
**顎の影に入った白いTシャツ（実測 11%）が素通り**して「白い紙 ✓検出」と表示され、
そのまま肌を測って a* が +10.5 も持ち上がり、`skinOk`(a*≤26) を超えて
「頬の位置で肌以外を測ってしまいました」という**見当違いの理由**で却下されていた
（2026-09-02 実機）。判定に進んでいれば、赤みを盛った肌で**全員がイエベ寄りに倒れる**系統誤差になる。

実写6枚の実測値（`whiteRef` の中身ごと）:

| 白基準の中身 | 明るさ wMax | 明るさ比(紙/肌) | 青寄り度 (B−R)/max | 彩度 (max−min)/max | |
|---|---|---|---|---|---|
| 白い紙 (8/30) | 219 | 1.24 | 0.000 | 0.014 | 正しい |
| 白い紙 (8/31) | 215 | 1.37 | −0.042 | 0.070 | 正しい |
| 白い紙 (9/4 A) | 227 | 1.27 | **+0.079** | 0.079 | 正しい |
| 白い紙 (9/4 B) | 228 | 1.35 | +0.066 | 0.066 | 正しい |
| 顎の影の白いTシャツ | **171** | 1.31 | +0.099 | 0.111 | 誤爆 |
| 首の肌 | **135** | **0.89** | −0.326 | 0.326 | 誤爆 |

- **★2026-09-03 に一度、青寄り度 0.05 で切って失敗している。**当時は正しい紙が2枚（0.000 / −0.042）
  しか無く、誤爆(+0.099)との間に余裕があるように見えた。翌 9/4 に正しい紙をあと2枚もらったら
  **+0.079 / +0.066** で、正しい紙のほうが誤爆に肉薄していた。**正しい紙を弾く**という、
  一番やってはいけない向きの誤りだった（本番 v1.17.0 で発生・v1.17.1 で修正）。
  → 青寄り度でも彩度でも、正しい紙と誤爆の差はもう **0.02** しかない。**どちらも分離には使えない。**
- **分離は白基準の明るさ `wMax` で行う。**正しい紙 215〜228 に対し誤爆 135〜171 で、**44 も離れている**。
  窓の光を拾って持つ紙は明るく写り、体に貼り付いた影の中の服は暗い、という物理的な差なので安定する。
- 採用した条件:
  | 定数 | 値 | 役割 |
  |---|---|---|
  | `PH_WHITE_MIN_LEVEL` | 190 | **主の分離軸。**正しい紙の最小 215 から −25、誤爆の最大 171 から +19 |
  | `PH_WHITE_MIN_LUMA_RATIO` | 1.05 | 肌より明るいこと。首の肌(0.89)を捕まえる |

- 却下メッセージは全て「白い紙が見つかりません」に統一し、補足文だけ理由ごとに変える。
  **首の肌のケースを色かぶりゲートより先に見る**のは、肌は彩度も高い(0.326)ため後回しにすると
  「照明の色が強く偏っています＝室内照明を消せ」という見当違いの指示になるため。
- 回帰ゲートは**両方向**に置いてある。誤爆を弾く側だけでは、また正しい紙を弾く方向へ締めてしまう。

## 記事への埋め込み

**colorlab は v1.12.0 から貼り方が2箇所に分かれている**（`snippet_colorlab.html` 参照）。

1. サイト共通の `<head>`（全ページ）に `<script src="...colorlab.iife.js" defer></script>` を1行
2. アプリを出したいページの本文に `<div id="colorlab-root">アプリを読み込み中…</div>` を1行

**本文側に `<script>` を置いてはいけない。** 設置先の blubel.jp / iebel.jp は Next.js の SPA で、
サイト内リンクから来ると React が本文を innerHTML 相当で差し込むため、その中の `<script>` は
ブラウザ仕様上まったく実行されない（＝アプリが永久に読み込まれない）。実測では、トップの
バナー経由だと `colorlab.iife.js` のリクエストが0件・`window.ColorLabApp` すら存在しなかった。
共通ヘッダーで常時読み込ませ、アプリ側が `#colorlab-root` を見つけて自動マウントする
（`mount()` の明示呼び出しは不要。従来の呼び出しも互換のため動く）。

ngpolice / mens は従来どおり本文にスニペットを貼る方式のまま。**同じ SPA 問題を抱えている**ので、
サイト内リンクからの流入がある導線では同じ2分割方式へ移すこと。

更新時は**必ずタグを上げて**（例 `@v1.0.1`）スニペットのURLも差し替える（`@main`はCDNキャッシュで反映が遅いため使わない）。

## 本番への反映手順（2026-09-03 時点の実物に合わせて記載）

**★本番は `snippet_colorlab.html` の2分割方式では入っていない。**実物は Shoppal 記事の
HTMLブロックに div とローダーを直書きする**インラインローダー方式**で、しかも
blubel と iebel で形が違う。差し替えるときは必ず現物を見てから触ること。

| ページ | 参照タグ（2026-09-03 実測） | ローダーの形 |
|---|---|---|
| https://www.blubel.jp/pages/personalcolor | `@v1.17.0` → v1.17.1 へ | `<script src>` 直書き + `onerror` + 再試行mount |
| https://www.iebel.jp/pages/personalcolor | `@v1.17.0` → v1.17.1 へ（2026-09-03 に v1.4.0 から移行済み） | blubel と同じ形に統一済み |
| https://www.blubel.jp/pages/police | `@v1.4.0`（ngpolice） | — |

反映は**バージョン文字列1箇所を書き換えるだけ**。blubel 側の現物は次の形になっている
（`ColorLabApp.mount` は v1.12.0 以降の自動マウントと二重にはならないので、そのまま残してよい）。

```html
<div id="colorlab-root">アプリを読み込み中…</div>
<script src="https://cdn.jsdelivr.net/gh/thecompany20220901-cpu/colorlab-embed@v1.17.1/dist/colorlab.iife.js"
  onerror="var e=document.getElementById('colorlab-root'); if(e) e.textContent='アプリの読み込みに失敗しました。ページを再読み込みしてください。';"></script>
<script>
(function () {
  var tries = 0;
  function mount() {
    var el = document.getElementById('colorlab-root');
    if (el && window.ColorLabApp && window.ColorLabApp.mount) { window.ColorLabApp.mount('#colorlab-root'); return; }
    if (++tries < 40) setTimeout(mount, 100);
  }
  if (document.readyState === 'loading') document.addEventListener('DOMContentLoaded', mount);
  else mount();
})();
</script>
```

- jsDelivr のタグ付きURLは `immutable`（`max-age=31536000`）でキャッシュされる。**同じタグに push し直しても反映されない**ので、
  変更したら必ず新しいタグを切ること。逆に、タグを変えれば purge 不要で即時反映される。
- **iebel 側は長らく v1.4.0 のままだった**＝v1.5.0〜v1.17.0 の改善（顔写真診断の実測方式・全画面撮影・
  ライブ判定・白基準の検証など）がすべて入っていなかった。2026-09-03 に**更新漏れと判断し、
  blubel と同じ上記の形へ揃える**方針とした（ローダーも動的生成方式から上のインライン方式へ）。
- **サイトごとの出し分けは無い。**BLUBEL / IEBEL のリンクや名前は `TYPES[].site` が持っており、
  診断タイプ（spring・autumn → IEBEL / summer・winter → BLUBEL）で決まる。ホスト名は一切見ていないので、
  **両サイトにまったく同じコードを貼ってよい。**
- v1.4.0 時代の `colorlab-profile`（localStorage）が残っていても壊れない。復元は try-catch で囲み、
  `TYPES` に無いタイプ名は捨てる作りになっている（旧形式・未知のタイプ名・壊れたJSON・空文字の
  4パターンで起動を実測確認、2026-09-03）。

### GTM（Googleタグマネージャ）で恒久設置する場合

設置先には全ページ共通の `<head>` 挿入欄が無い（Fulmo 回答）。GTM のカスタムHTMLタグで代替できる。
**本文側の `<div id="colorlab-root">` は必ず残すこと。**GTM はスクリプトを差し込めるだけで、
アプリを「どこに出すか」は知らないため。本文からは `<script>` だけを消す。

GTM に入れるタグの中身（これだけ）:

```html
<script src="https://cdn.jsdelivr.net/gh/thecompany20220901-cpu/colorlab-embed@v1.17.1/dist/colorlab.iife.js"></script>
```

`mount()` の呼び出しは不要。v1.12.0 の自動マウント（`#colorlab-root` を自分で見つける +
MutationObserver + pushState フック）がそのまま働く。**SPA遷移でリロード無しにマウントされることを
2パターンで実測確認済み**（2026-09-04・`45_gtm_spa_allpages.png` / `45_gtm_spa_historychange.png`）。

| トリガー構成 | 結果 | 備考 |
|---|---|---|
| 全ページ（Page View）で先に読み込む | リロード無しでマウント成功 | 単純だが無関係なページでも 367KB(gzip) 読む |
| パス限定の Page View + 履歴の変更 | リロード無しでマウント成功 | **推奨。**診断ページ以外では読み込まない |

- **★パス限定の Page View だけでは足りない。**Next.js のクライアント遷移では Page View が発火しないため、
  サイト内リンクから来ると永久にタグが出ない。**「履歴の変更」トリガーとの2本立てが必須。**
- タグの配信オプションは「1ページにつき1回」。「document.write をサポートする」はチェックしない。
- blubel / iebel はコンテナが別なので、**両方に同じ設定を入れる**。

## 診断イラスト・勝ち色データ（対象1〜3 / 2026-09-02〜）

「12タイプ診断の設問イラスト」「結果画面の勝ち色の体系化」「コーデ提案・採点のイラスト」は、
すべて **既存データ・既存素材からの機械生成**で、色・効果・素材を新規に創作していない。

### 設問イラスト（対象1）

- 土台は `C:/Users/newfa/instagram/renderer/assets/faces/` の4タイプ顔イラスト（IG表紙で使用中の受領素材）。
  肌・頬・髪・服・唇・瞳の**色だけ**を Lab 平行移動で差し替える。L* の相対差（陰影・線）は保存されるので、
  A/B は「同一人物・同一構図で色だけが違う」ことが構造的に保証される。
- 差し替える HEX は `Q12[].illust.left/right` が既に持っている値をそのまま使う（生成側は色を決めない）。
- 素材が無い2問だけ例外:

    血管色は `Q12[4].illust` の値。A/B でパスは完全に同一で、変わるのは血管色だけ。
  - Q10（金属）… 首元の素材1枚を共有し、その上にゴールド/シルバーのアクセだけを SVG で重ねる。
